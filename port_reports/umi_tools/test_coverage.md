## Interpretation for this port

The raw numbers above are misleading and need the mapping below; recorded in
full in `08_validation.md` § Coverage parity.

The Python side reports **3 tests** because its suite is three `pytest`
functions, one of which is parameterised over `tests/tests.yaml` into 70
actual cases. The script counts functions, not parameterisations.

| Python test | Rust counterpart | Status |
|---|---|---|
| `test_script[...]` (70 parameterised CLI cases) | **the same suite, run unchanged against the Rust binary** | 67/70 pass; the 3 failures are documented deviations D12/D13 (remote reference URLs, CRAM output of sequence-less records) |
| `test_script_has_main[script]` — asserts each module defines `main` | `cli::run`'s dispatch table plus `cli::tests::usage_lists_every_tool` | covered |
| `test_style` — `pycodestyle` over the source | `cargo fmt --check` and `cargo clippy -- -D warnings`, both clean | covered |

The 355 "Rust-only" tests are not a surplus to be explained away: the Python
package has **no library-level unit tests at all** (see `01_audit.md`
§ Existing tests), so every unit test in the port is new coverage of behaviour
that was previously only exercised end to end. Of those, the fixture-driven
parity suites (`crates/core/tests/*.rs`) compare against values dumped from the
live Python package rather than against expectations written from memory.
